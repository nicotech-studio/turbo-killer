# CPU frequency monitoring · 1.3.0

This document records implementation and local validation for builds 4–7.
See the [1.3.0 release notes](../releases/1.3.0/en.md) for the public feature list;
publication status and download assets are tracked in GitHub Releases.

## Behavior

- The existing menu bar icon can show a frequency in GHz next to it. The compact
  popover displays the same value and opens a separate Frequency Monitor window.
- The window shows the last 5 minutes, 15 minutes or hour. Pale red backgrounds
  represent confirmed Turbo Boost enabled intervals; pale blue represents disabled
  intervals. Unknown state and missing samples remain neutral. Colors indicate
  the control state, not whether the CPU was actually running above nominal.
- Settings → Monitoring offers one shared 1/2/5/10-second sampling interval
  (default 2), menu bar number visibility, and background history recording.
- Samples are kept in memory for this session only, up to one hour and 3,602
  points. With background recording disabled, new history is retained only while
  the history window is open. Menu bar and popover values can still update.
- Sleep, unavailable data, pauses and interval changes break the line. Hovering
  over a sampled interval shows its timestamp, average frequency and state.

## Data source and lifecycle

The signed app uses the existing code-signature-checked XPC service. A new,
fixed-purpose selector asks for the next CPU frequency sample at one of four
allowed intervals. It cannot select executables, samplers or command arguments.
Older helpers fail the compatibility health check and use the existing repair
flow when the popover opens. At launch, a compatible, already registered helper
can be used without opening the popover or registering a new service.

The helper maintains one `/usr/bin/powermetrics --samplers cpu_power --format
plist --buffer-size 0 --sample-rate N` process. Its NUL-separated property lists
are framed across pipe reads with a 1 MiB bound. The `processor.freq_hz` value is
the processor-wide average execution frequency reported by powermetrics; it is
not a nominal CPU specification or a maximum across cores. `elapsed_ns` defines
the averaging interval, ending at receipt of the frame. Arrival timestamps can
have scheduling latency and do not locate an external state change precisely.

Reference for the Intel plist schema: Chromium's original
[powermetrics monitor](https://chromium.googlesource.com/chromium/src/+/a9ed17edd6831510d2d50680824740a485ae25d6/tools/telemetry/telemetry/internal/platform/power_monitor/powermetrics_power_monitor.py).
The implementation is independent and does not copy its code.

Each request is bounded by the sample interval plus four seconds in the helper
and six seconds in the app. Tool exit, invalid data and output overflow fail the
request without blocking Turbo Boost control. The app backs off for at least
five seconds on failures. Interval changes invalidate old replies and restart
the sampler. Shutdown waits for the stop request; after a client crash a
monotonic lease stops unattended sampling within approximately 35 seconds.
Termination has a two-second kill fallback. Pipe readers drain stdout and stderr
independently, including EOF cleanup.

Turbo Boost observations remain independent of frequency acquisition. They are
recorded on state reads and after operations; an in-flight toggle records an
unknown interval. Confirmation expires after 45 seconds without another read.
External changes may only be discovered by the existing 30-second state poll.
This avoids running `kmutil showloaded` on every frequency sample.

The historical kernel extension and its integrity policy are unchanged.

## Local validation

- Debug and Release builds, targeting x86_64 / macOS 13+.
- `bash tools/test-frequency.sh`: CPU plist parsing and validation, fragmented
  and batched frames, bounded output, historical state boundaries and expiry,
  duplicate rejection, line gaps, history retention, preference persistence,
  visibility demand, interval changes, obsolete reply rejection, error handling,
  sleep/wake and shutdown. The helper's interval validation and unprivileged
  tool-exit path are also exercised without installing a helper.
- `bash tools/test-status-model.sh`: existing Turbo Boost state regressions.
- `python3 tools/check-localizations.py`: 17 languages, including the new
  telemetry strings and integer placeholders. Translations have not received
  independent native-speaker review.
- The existing packaging script runs all 13 kernel bundle integrity checks,
  verifies the original bundle again in the archive and mounted DMG, and signs
  and verifies the helper, app and DMG using Developer ID. This is not notarization.
- `tools/render-previews.sh` renders actual SwiftUI views with synthetic data in
  an isolated temporary bundle, without connecting to XPC or loading a kext.
  New history and monitoring-settings snapshots cover all 17 languages.
  Chinese, German, Russian, Arabic and Hebrew layouts receive visual inspection;
  native settings tab chrome still needs an interactive check.

## Hardware acceptance still required

This machine has an Intel processor, but invoking powermetrics requires an
administrator password (`sudo -n` cannot authorize it). Therefore the real
frequency data path, accuracy, idle behavior, CPU overhead and battery impact
have not been claimed as verified. No real Turbo Boost toggle was performed.

Before public release:

1. Install the signed trial app, open the popover and allow or repair the updated
   background helper if macOS requests it. Verify numbers change under idle and
   sustained CPU load and agree across all three displays.
2. Switch Turbo Boost in each direction and inspect the background transition.
   Check failure and approval flows still work. Compare under the same workload.
3. Change all intervals, close/reopen the history window, disable background
   recording, sleep/wake the Mac, quit, and terminate the app unexpectedly.
   Confirm no orphan powermetrics process remains after the documented lease.
4. Measure the app and helper's CPU/wakeup overhead at 1, 2, 5 and 10 seconds.
   Validate battery behavior and Intel/macOS compatibility before choosing the
   final default and publishing release notes or website changes.

## Compact interface iteration · build 5

The owner supplied screenshots showing frequency readings in the live menu bar
and popover, then requested smaller typography and a more compact layout. This
iteration changes the interface, with the existing sampling and control paths
retained. It does not add an accuracy or energy-profile acceptance claim.

- The menu bar composites the unchanged 22 × 18 pt icon with an explicitly drawn
  11 pt frequency and 10 pt GHz unit, retaining template-image appearance and
  the frequency accessibility value.

  link. Sampling explanations move to a hover hint. Long translations may wrap
  the link onto another row rather than clipping it.

  All compiler-extracted strings are present in the catalog. Actual SwiftUI
  components were rendered for all 17 locales in both appearances, including a
  menu bar label preview. Chinese, French, German and Arabic were inspected.

## Menu contrast and base-frequency reference · build 6

- Menu bar glyphs use an opaque template mask. The former dynamic label color
  carried alpha into the template and dimmed the text relative to the icon.
  The native status bar still chooses the final foreground for its appearance.
- Removed the visible horizontal-axis title. Removed the 24 pt position-scale
  padding on each side. Interior time ticks retain readable labels without
  changing the full time-to-position mapping. Unsampled periods remain empty.
- Added a subtle dashed base-frequency reference, an exact vertical-axis value
  and a legend/help entry. Nearby ordinary tick labels yield space when needed.
  Reference values also participate in the vertical scale domain.
- CPUBaseFrequency reads the Intel brand string and static hw.cpufrequency once
  per monitor. Only plausible matching values are accepted (within 10 MHz or
  0.5%); missing, unsupported or inconsistent information hides the reference.
  hw.cpufrequency alone is deliberately insufficient: Apple marks this selector
  deprecated and describes its dependence on power-management modes in
  [the XNU header](https://github.com/apple-oss-distributions/xnu/blob/main/libkern/libkern/sysctl.h).
- This machine reports an i7-9750H, a 2.60 GHz brand suffix and 2,600,000,000 Hz
  static clock. A standalone read using the new detector returned 2.6 GHz.
  [Intel specifies a 2.60 GHz base](https://www.intel.com/content/www/us/en/products/sku/191045/intel-core-i79750h-processor-12m-cache-up-to-4-50-ghz/specifications.html).
  The reference is not a floor, a cap, or the current sampled execution rate.
- Debug/Release builds, frequency/base-detection regressions, existing status
  regressions, 17-language catalog coverage and compiler-extracted string
  coverage passed. All 17 locale previews were generated; Chinese light,
  German dark and Arabic dark charts and the menu label were inspected.
  Packaging rechecked all 13 kext integrity cases and verified the signed app,
  helper and mounted DMG. The helper and sampling protocol are unchanged.

## Base-frequency legend clarification · build 7

The vertical axis retains a short numeric reference label. The dashed-line
legend now pairs its localized name with its exact value and unit (for example,
“基础频率 2.60 GHz”). Its hover help explains that this is the CPU's nominal base
frequency, not the current, minimum or maximum frequency.

This avoids widening the vertical axis for long translations. The existing
legend uses a two-row layout when the full row cannot fit. In addition to
17-locale light/dark previews, 540 pt window previews were generated; French and
German narrow-window layouts were visually checked. Debug/Release builds,
17-language catalog and extracted-string coverage, and packaging/signature/kext
integrity checks passed. Sampling and base-frequency detection are unchanged.
